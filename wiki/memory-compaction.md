# Memory compaction and manual cleanup

- GEOS compacts the global heap during allocation pressure and in the idle-time heap scrub thread. `CompactHeap` is a near, internal routine (`Library/Kernel/Heap/heapCore.asm`; `Library/Kernel/Heap/heapScrub.asm:HeapScrubThread`), with no application-level force-collection API. See also `TechDocs/Markdown/Concepts/cmemory.md`, section 15.2.2.4.
- The scrub thread runs at `PRIORITY_IDLE` (`Library/Kernel/Heap/heapInit.asm:HeapStartScrub`). It waits on `scrubSem` for `SCRUB_TIMEOUT = 60 * INTERRUPT_RATE` ticks, one minute (`Library/Kernel/Heap/heapConstant.def`; `Library/Kernel/kernelConstant.def:INTERRUPT_RATE`). On timeout it compacts the heap. `FindFree` can wake it earlier through `VScrub` near the danger level (`Library/Kernel/Heap/heapCore.asm`; `Library/Kernel/Heap/heapScrub.asm`). Thus there is no required continuous idle period; one minute is its periodic wake-up interval, subject to idle-priority scheduling.
- Applications must free their own allocated blocks and chunks with `MemFree` and `LMemFree`; global compaction rearranges blocks and may discard or swap eligible blocks, but does not reclaim allocated data just because the application no longer uses it (`TechDocs/Markdown/Concepts/cmemory.md`, sections 15.2.2.3-4 and 15.3).
- To compact a specific LMem heap and return its unused space to the global heap, lock its block and call `LMemContract`. The block remains at the same address, but chunk pointers become invalid (`TechDocs/Markdown/Routines/rrouth_l.md:LMemContract`; `Library/Kernel/LMem/lmemCode.asm:LMemContract`; `CInclude/lmem.h`).
- VM file compaction is threshold-driven. In non-backup mode, it may happen on `VMUpdate`; in backup mode, on `VMSave`, `VMSaveAs`, or `VMRevert` (`TechDocs/Markdown/Concepts/cvm.md`, section 18.2.3.3).
- `VMOpen(..., VMO_TEMP_FILE, ...)` creates a temporary file in the passed directory and appends its generated name to the supplied name buffer. `VMClose()` closes it but does not delete it; callers that own temporary VM files must also `FileDelete()` the generated name. The VM manager's temp-file path calls `FileCreateTempFile()` in `Library/Kernel/VMem/vmemHigh.asm` (`VMOpen`) and later `FileClose()` in the same file (`VMClose`); `Library/Breadbox/Ijgjpeg/SUPPT/JMEMGEOS.c` shows the explicit close/delete pattern.
- `SysGetInfo(SGIT_LARGEST_FREE_BLOCK)` reports the largest allocatable block in bytes, but is not a cheap probe: `SGI_LargestFreeBlock()` calls `FindFree` with 0xffff, whose special path calls `CompactHeap` over the entire heap before returning the largest block. Do not poll it in a per-image or per-row diagnostic path (`Library/Kernel/Sys/sysStats.asm:SGI_LargestFreeBlock`; `Library/Kernel/Heap/heapCore.asm:FindFree`). `SGIT_NUMBER_OF_FREE_HANDLES` reports free kernel handles (`CInclude/sysstats.h`). BbxBrow's `EnforceObjCacheHandleLimits()` begins updating VM caches below 500 free handles to stay above a documented 200-handle system limit (`Appl/Breadbox/BbxBrow/navigate/NAVCACHE.goc`).
- The VM manager normally trims each VM file from 250 resident handles to 150 (`VMEnforceHandleLimit()` in `Library/Kernel/VMem/vmemLow.asm`, called by `VMAlloc()` in `vmemHigh.asm`). This per-file policy can still leave global handles scarce across several cache files. BbxBrow's explicit `VMEnforceHandleLimits(file, 20, 20)` is a stronger pressure response; its progress callback checks it while a graphic keeps adding VM blocks after the first cache insertion (`htmlview/ImportG.goc`, `navigate/NAVCACHE.goc`).
- A failed reload of a discarded code resource can leave the movable-call target segment zero: `FullLockReload` calls `DoReAlloc` with `HAF_STANDARD_NO_ERR` and then reads `HM_addr`; `RCI_call` raises `RCI_CALL_WANTS_TO_LEAP_INTO_SPACE` when its resulting call-vector segment is zero (`Library/Kernel/Heap/heapLow.asm:FullLockReload`, `Library/Kernel/Geodes/geodesResource.asm:RCI_call`). A stack stopped in `LockDiscardedResource` can therefore reflect heap pressure rather than a null source-level callback.

- IJGJPEG's active virtual-array implementation is in `Library/Breadbox/Ijgjpeg/SUPPT/JMEMMGR.c` (`realize_virt_arrays`, `ArrayStoreLockBlock`, `access_virt_sarray/barray`), rather than the backing-store routines in `SUPPT/JMEMGEOS.c`. It uses one temporary VM file per decoder image pool, trims resident rows with `VMEnforceHandleLimits(file, 20, 30)`, and closes/deletes that file in `free_pool(JPOOL_IMAGE)`. Writable rows are marked dirty before unlocking; current row locks must also be released during error cleanup.
- Native `VMAlloc` allocates row memory through `VMGetMemSpace`, which adds `HAF_NO_ERR` (`Library/Kernel/VMem/vmemHigh.asm:VMAlloc`, `vmemLow.asm:VMGetMemSpace`). To recover from an initial row-memory shortage in a decoder, allocate with checked `MemAlloc(..., HAF_ZERO_INIT)` and transfer ownership with `VMAttach(file, 0, rowH)` instead. Native VM metadata allocation and paging still follow kernel failure behavior.

- `GLOBAL_HEAP_IS_CONGESTED_SO_THREAD_IS_SLEEPING` is the retry warning in `AllocationFailure`, not a fatal error or a free-handle count check. Its callers include `AllocHandleAndBytes` and expanding `DoReAlloc` when `HAF_NO_ERR` is set (`Library/Kernel/Heap/heapLow.asm`), and `MemSwapIn` (`heapSwap.asm`). It releases one heap semaphore acquisition, warns, sleeps for `ALLOCATION_RETRY_WAIT_TIME = 20` ticks, then reacquires the semaphore. `NUMBER_OF_ALLOCATION_RETRIES = 100` controls retries before `NotifyAllocError` (`heapConstant.def`). The warning alone does not identify the requesting subsystem; inspect the stopped thread stack.
